Several correctness and privacy boundaries therefore remain static risks or unknowns, not demonstrated runtime defects or production compliance failures.

## 2) Architecture and product boundary
The inspected reading-gate boundary is narrower and more mixed than the prior draft claimed:
- Unity `GateController.TriggerGate(...)` sets `currentGateId`, `currentRetries`, `maxRetries`, builds a `GateTriggeredPayload`, and calls `BridgeManager.Instance.SendGateTriggered(payload)`.[8]
- React Native `useASR().validate(...)` either POSTs gate text, student ID, difficulty, `audioBase64`, metadata, `attemptNumber: 1`, and optional bearer auth to `${apiBaseUrl}/api/v1/asr/validate`, or falls back to `validateOffline(...)`.[9]
- FastAPI `validate(...)` checks auth when enabled, validates/caps base64 audio, calls `providers.route_and_transcribe(...)`, scores the returned transcript, and computes `retriesRemaining` from the supplied `attemptNumber`.[10]
- Unity `OnAsrResult(...)` handles `PASS`/`PARTIAL`/`FAIL`, and `OnGatePassed(...)` calls `FindObjectOfType<SceneSequencer>()?.OnGateCleared();`; the only inspected `SceneSequencer` implementation in the same file is explicitly marked `Stub` and only logs `"[SceneSequencer] Advancing to next gate/scene"`.[8]

That is enough to classify the repo as an implementation with visible prototype edges, not as a pure prototype and not as a fully traced production game loop. The sample does **not** prove that the inspected `SceneSequencer` stub is the runtime one, nor that another sequencer or bridge path does not exist. It also does not prove on-device reachability from spoken audio to visible scene advancement.

The broader repo shape remains a five-service Node workspace plus Python ASR and a separate mobile package, with README claims for API gateway/WAF, Kafka, analytics, Docker, and deployment flow.[2][4][5] Those broader platform claims were not independently revalidated here.

## 4) Five-discipline assessment
- **Correctness / code review:** applicable. The sampled reading-gate path is real code, but it contains static correctness gaps around offline fallback semantics, attempt propagation, and gate-ID validation.[8][9][10]
- **Automation / testing:** applicable. CI is broader than the prior draft suggested, but the pinned run is historically red because the mobile typecheck failed, `Mobile audit` was skipped in that job, and the ASR “≥95% coverage” label is not backed by the inspected command/config.[5][7][11][12][13]
- **DevOps / operations:** applicable. `build-images` depends on five prerequisite jobs, so mobile failure blocks later artifact building.[5] No restore, rollback, deploy, or staging observations were inspected.
- **OWASP / security & privacy:** applicable. The sampled boundary includes optional bearer auth, an auth-off mode, base64 audio transport, student-role enforcement, and provider egress.[9][10] Secret handling, provider retention, transport security in production, and log redaction remain uninspected.
- **UI / UX / accessibility:** partially applicable. `GateController` includes an accessibility-oriented `allowBypassAfterTimeout` setting and retry/exhaustion prompts in comments/logs, but no inspected child-facing UI copy, no verified offline error UX, and no verified scene progression or device behavior.[8] No COPPA/legal UI claim should be made from this sample alone.

## 5) Production blockers and owner questions
Blockers:
1. A corrected candidate SHA with a successful CI run separate from the historical failing SHA.
2. Bridge/runtime trace evidence for `mobile/src/unity/bridge.ts`, `BridgeManager`, `LitPlayBridge`, and the real scene/progression assets.
3. Owner-approved staging/device access to verify gate progression, offline-provider-unavailable handling, and rollback/recovery behavior.
4. Privacy/security-owner evidence for production ASR endpoint, transport/TLS path, `auth_required` configuration, provider egress, retention/deletion, and log handling.
5. An authoritative ASR coverage gate that measures the intended scoring scope instead of relying on an unlabeled assumption.

Owner questions:
1. Which component is authoritative for gate-attempt counting in production: Unity state, RN hook state, progress-service session state, or a combined contract?
2. Is the inspected `SceneSequencer` stub the runtime implementation, a placeholder compiled into dev scenes only, or dead code shadowing another sequencer?
3. What is the production ASR endpoint and provider set, and where are retention/deletion terms recorded?
4. What exact public wording is approved for child-audio handling, parental consent, and COPPA/privacy claims?
5. Which candidate build, signing path, and rollback runbook are required before a mobile release is considered releasable?
